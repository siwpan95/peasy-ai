# TextCNN 接入对话链路（端到端）

> 本文记录把 P2 的 TextCNN 真正接进 `AICore` 对话链路的过程与实测结论，
> **包括那个不利的结论** —— 只报好消息等于没做验证。

## 1. 接入方式：离线训练 + 运行期加载

TextCNN 训练需数秒（马尔科夫只要毫秒级），直接放进启动路径会拖慢
`AICore()` 的零参数启动。因此拆成两步：

```bash
python tools/train_textcnn.py --full     # 离线：全量语料训权重 → data/textcnn_weights.json
```

```json
"neural": { "enabled": true, "weights": "auto", "corpus": "auto" }
```

| 阶段 | 耗时（实测） |
|---|---|
| `AICore()` 默认启动（neural 关闭） | **225 ms** |
| `AICore()` 启用 neural（加载 1.4MB 权重 + 建索引） | **89 ms** |
| 单条回复生成（neural） | 55–135 ms |

权重 1.4MB，属可再生产物 → 已 `.gitignore`。

## 2. 过程中修掉的两个真 bug

### 2.1 只加载权重、漏建检索索引 → neural 形同虚设

加载权重只恢复了「**怎么说话**」的语言模型，而「**说什么**」由检索索引决定。
初版只在「无权重」分支里建语料，导致加载权重后 `pairs=0`、
`match()` 恒返回 `None` —— 链路里挂着 NeuralMatcher，却一条回复都没它产出。

> 教训：**接入 ≠ 生效**。必须验证它真的在竞争里出过场，而不是只看 `ready=True`。

### 2.2 生产权重必须用 `--full`

权重若按默认的 80/20 划分训练，则留出那 20% 的原文对 CNN 是**未见过**的；
运行期检索到它们时会给出很低的概率 → 置信度被压到 0.10–0.16，永远输给马尔科夫。
生产环境应把语料全量纳入训练（无留出），留出集只用于**评估**。

## 3. 核心结论：自由生成不是 CNN 的强项（实测）

启用 neural 后，同输入下两个匹配器的置信度对比：

| 输入 | Neural 置信度 | Markov 置信度 | 实际胜出 |
|---|---|---|---|
| 什么是深度学习 | 0.1534 | 0.7500 | Markov |
| 感知检定是什么结果 | 0.1618 | 0.7500 | Markov |
| 调查尸体与铜镜 | 0.1051 | 0.7500 | Markov |

**根因不是实现问题，而是模型性质差异**：

- n-gram 是**记忆型**：回放训练语料里的原句时，perplexity 极低（近似 3.4），
  于是「相对均匀基线的增益」很高（0.79–0.91）。
- CNN 是**泛化型**：它不会精确记住原句，对同一句的似然反而更低。

而本项目的置信度定义恰恰是「生成序列的似然增益」——
**这个口径天然偏向记忆型模型**。于是出现了一个不矛盾但容易误读的现象：

> 留出集上 CNN 的预测精度更高（top-1 43.95% vs 34.81%，见 `BASELINE_P2.md`），
> 但自由生成时马尔科夫更受这个置信度口径的偏爱。

这不是谁错了，而是**两个指标在衡量不同的东西**：
teacher-forcing 的预测精度 ≠ 自由生成的质量。P0 就踩过一次同类陷阱
（「指标上升但端到端回复碎片化」），这里是它的另一个面。

## 4. 因此采用的落地策略

1. **neural 默认 `enabled: false`** —— 它已在链路上、开箱可启用，
   但在当前口径下不参与竞争更合理；需要实验时打开即可。
2. **CNN 的正确定位是「打分器 / 重排序」，而非自由生成器**：
   它的强项是泛化评估（对未见过的文本给更准的预测），
   适合给候选回复打分排序；生成仍交给马尔科夫（回放真实语料质量更高）。
   这条改造留作后续。
3. 若坚持让 neural 参与生成竞争，应改用**任务相关性**为主、
   模型似然为辅的置信度定义，避免用似然口径跨模型比较记忆型与泛化型。
